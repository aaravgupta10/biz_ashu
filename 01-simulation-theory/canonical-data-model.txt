# Purpose

The Canonical Data Model defines the shared vocabulary of the Simulation Engine.

Every component must exchange information using these canonical objects.

This guarantees:

- consistency
- interoperability
- explainability
- versionability
- extensibility

The CDM is independent of implementation language, database technology, or API design.

---

# Design Principles

Every object must satisfy five principles.

## 1. Canonical

There should only be one definition for each concept.

Never create duplicate concepts.

---

## 2. Immutable History

Objects should preserve historical state whenever possible.

---

## 3. Extensible

New properties may be added.

Existing meaning must never change.

---

## 4. Explainable

Every object should be understandable by humans.

---

## 5. Versioned

Every object supports schema evolution.

# Now here's the biggest thing I want to change.

I think we've accidentally started designing a traditional software system.

I don't think this should be one.

I think this should be an **event-driven platform**.

Instead of:


Crawler

↓

Database

↓

Simulation

↓

Report


Think


ArtifactUploaded

↓

ObservationCompleted

↓

EnvironmentCreated

↓

SimulationStarted

↓

SimulationCompleted

↓

InsightsGenerated

↓

RecommendationsGenerated

↓

ReportPublished


Every stage emits events.

Every stage listens to events.

That architecture has enormous benefits:

- easier scaling,
- retry failed jobs,
- parallel simulations,
- real-time progress updates,
- easier observability,
- cleaner AI orchestration.

## One final proposal—and I think it's the biggest architectural decision we've made so far.

I don't think we're building a web application.

I think we're building a **simulation operating system**.

Everything we've defined so far—the Synthetic Human Model, Behavioral Model, Decision Engine, Canonical Data Model—looks much closer to the internals of a game engine than a CRUD SaaS.

That realization should influence every engineering decision going forward. Instead of asking, "What's the next API endpoint?", we should ask, "What subsystem does the simulation OS need next?"

If we keep that mindset, I think the architecture will remain coherent even as the product grows far beyond the initial SaaS use case.
